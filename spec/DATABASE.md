# Database — source of truth and rules of engagement (v3.2, go-live)

The base schema is 41 tables + 5 triggers across 3 files, validated by
execution against PostgreSQL 16 (not just reviewed):

- `db/schema.sql`   — tables, constraints, indexes (incl. exclusion constraint)
- `db/triggers.sql` — the 5 trigger functions. **v2:** trigger 1 refuses
  negative payouts; trigger 3 now ALSO flips the booking to 'confirmed',
  writes the `booking_status_history` row, and rejects accepts on
  already-resolved (rejected/expired) assignments. The v1 test evidence
  covers the old behavior — the v2 launch-gate tests in DISPATCH_FLOW.md
  MUST be run before go-live.
- `db/seed.sql`     — required `status_types` rows (deployment gate).
  **v2:** now includes all four new booking statuses (`payment_pending`,
  `abandoned`, `failed_no_pujari`, `disputed`) — seed.sql is the single
  source of seed truth; the identical rows in migration 002 below are a
  redundant idempotent safety, not an alternative.

**v2 adds migration 002** (DDL below, verbatim) — money-safety, dispatch
state, geo, and presence objects required by DISPATCH_FLOW.md v2. Migration
002 MUST be applied before the first live payment.

**v3 adds migration 003** (DDL below, verbatim) — dual payment models
(`full_online` | `advance_balance`). Migration 003 MUST be applied before
checkout offers both options to customers.

**v3.1 adds migration 004** (DDL below, verbatim) — persist
`bookings.razorpay_order_id` for idempotent checkout resume on duplicate
submit. Migration 004 MUST be applied before go-live.

**v3.2 adds migration 005** (DDL in `db/migration_005.sql`) — address `geom`
sync trigger + refund total cap per payment. See `spec/plans/SPEC_AMENDMENTS.md`.
Apply before production money ops go live.

**v3.2 adds migration 006** (DDL in `db/migration_006.sql`) — duration guard
(trigger 5 `NULLIF`, `CHECK (duration_minutes > 0)`, backfill). See
`spec/plans/SPEC_AMENDMENTS.md` §12. Apply before go-live.

## Alembic integration — the one rule that matters

**Migration 001 is the raw SQL, verbatim.** Use `op.execute()` on the file
contents of order: schema -> triggers -> seed. **Migration 002 through 006 are
the DDL blocks below, verbatim, the same way.** Then map SQLAlchemy models onto the
existing tables. NEVER let `alembic revision --autogenerate` produce the
initial schema, and review every later autogenerated migration for attempts to
drop things it doesn't understand — specifically:

- `ex_bookings_pujari_no_overlap` and `ex_bookings_intended_no_overlap`
  (EXCLUDE USING gist — autogenerate does not model exclusion constraints and
  may emit a DROP)
- partial unique indexes (`ux_slot_holds_active`, `ux_bookings_no_duplicate_submit`,
  `ux_addresses_one_default_per_user`, `ux_booking_assignments_one_live`,
  `ux_payments_one_success_per_booking`, `ux_refunds_one_active_per_payment`)
- all triggers and their functions (5 base in triggers.sql — trigger 3 is the
  v2 accept-resolution version — plus `trg_guard_booking_cancel` from 002)
- `ck_payment_splits_net_nonneg`
- PostGIS `GEOGRAPHY` columns and their gist indexes

If an autogenerated migration touches any of the above, the migration is wrong.

## Migration 002 — DDL (apply verbatim after 001)

Canonical file: **`db/migration_002.sql`** (same contents as the block below).
Apply with `psql -f db/migration_002.sql` or Alembic `op.execute()` on the
file contents.

```sql
-- ---- extensions -----------------------------------------------------------
CREATE EXTENSION IF NOT EXISTS postgis;

-- ---- bookings: unpaid lifecycle + committed pujari + hold linkage ----------
-- intended_pujari_id = the COMMITTED pujari: the customer's choice at checkout
-- (direct mode), and ALSO written by trigger 3 on every accept (both modes) so
-- ex_bookings_intended_no_overlap covers the whole accepted population. The
-- original customer choice is auditable via dispatch_mode + booking_assignments.
ALTER TABLE bookings ADD COLUMN intended_pujari_id UUID REFERENCES pujaris(id);
ALTER TABLE bookings ADD COLUMN hold_id UUID REFERENCES slot_holds(id);
ALTER TABLE bookings ADD COLUMN paid_at TIMESTAMPTZ;
ALTER TABLE bookings ADD COLUMN dispatch_mode VARCHAR(10) NOT NULL DEFAULT 'broadcast'
    CHECK (dispatch_mode IN ('direct','broadcast'));

-- THE paid-slot guarantee: two PAID, uncancelled bookings can never target the
-- same pujari's overlapping time window, regardless of app-layer bugs. Backstop
-- for BOTH the hold-expiry-vs-late-payment race (fires in the webhook) and the
-- cross-mode overlap hole (fires at accept, because trigger 3 writes
-- intended_pujari_id on every accept — a broadcast accept by a pujari who has
-- a paid direct booking pending elsewhere raises here).
ALTER TABLE bookings ADD CONSTRAINT ex_bookings_intended_no_overlap
    EXCLUDE USING gist (
        intended_pujari_id WITH =,
        tsrange(scheduled_date + scheduled_time,
                scheduled_date + scheduled_time + make_interval(mins => duration_minutes)) WITH &&
    ) WHERE (intended_pujari_id IS NOT NULL AND paid_at IS NOT NULL AND cancelled_at IS NULL);

-- ---- slot_holds: "any pujari" holds + conversion audit ---------------------
ALTER TABLE slot_holds ALTER COLUMN pujari_id DROP NOT NULL;  -- NULL = "any pujari" checkout; btree uniques treat NULLs as distinct, so ux_slot_holds_active is unaffected
ALTER TABLE slot_holds ADD COLUMN converted_at TIMESTAMPTZ;   -- set (with released_at) when payment succeeds

-- ---- refunds: money movement is a state machine, never an inline API call --
CREATE TABLE refunds (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    payment_id          UUID NOT NULL REFERENCES payments(id),
    booking_id          UUID NOT NULL REFERENCES bookings(id),
    amount              DECIMAL(10,2) NOT NULL CHECK (amount > 0),
    reason              VARCHAR(30) NOT NULL
                          CHECK (reason IN ('customer_cancel','no_pujari','late_payment','admin_override')),
    status              VARCHAR(20) NOT NULL DEFAULT 'pending'
                          CHECK (status IN ('pending','processing','succeeded','failed_permanent')),
    gateway_refund_id   VARCHAR(100) UNIQUE,   -- Razorpay's RETURNED refund id (rfnd_...). NOT the idempotency key: a value the gateway returns cannot dedupe the call that obtains it. The key we SEND is refunds.id — client-generated, stable across retries.
    attempt_count       SMALLINT NOT NULL DEFAULT 0,
    next_attempt_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_error          TEXT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_refunds_one_active_per_payment
    ON refunds (payment_id) WHERE status IN ('pending','processing');
-- Covers BOTH the worker poll (pending past next_attempt_at) and the
-- stuck-'processing' requeue: taking a row sets status='processing' AND
-- next_attempt_at = now() + 30 min; a 'processing' row past next_attempt_at
-- is a crashed worker and requeues to 'pending' (reconciliation arbitrates
-- against Razorpay's actual state). Without the requeue, a crash between
-- 'processing' and completion strands the row forever AND blocks any new
-- refund for that payment via ux_refunds_one_active_per_payment.
CREATE INDEX ix_refunds_worker ON refunds (next_attempt_at)
    WHERE status IN ('pending','processing');

-- ---- payments: at most one successful capture per booking ------------------
CREATE UNIQUE INDEX ux_payments_one_success_per_booking
    ON payments (booking_id) WHERE status = 'success';

-- ---- sweep support: abandoned-payment scan needs an index; the status can't
-- be a partial-index predicate without hardcoding an id (conventions forbid) --
CREATE INDEX ix_bookings_status_created ON bookings (status_id, created_at);

-- ---- money floor: belt-and-suspenders with the trigger-1 raise — a fee/GST
-- misconfiguration can never persist a negative pujari payout ----------------
ALTER TABLE payment_splits ADD CONSTRAINT ck_payment_splits_net_nonneg
    CHECK (net_pujari_amount >= 0);

-- ---- dispatch state: rounds, radius, exhaustion (see DISPATCH_FLOW.md) -----
CREATE TABLE booking_dispatch_state (
    booking_id       UUID PRIMARY KEY REFERENCES bookings(id) ON DELETE CASCADE,
    round            SMALLINT NOT NULL DEFAULT 0,
    radius_km        DECIMAL(5,1) NOT NULL DEFAULT 3.0,
    max_rounds       SMALLINT NOT NULL DEFAULT 4,
    last_dispatched  TIMESTAMPTZ,
    exhausted_at     TIMESTAMPTZ
);

-- ---- offer integrity: one live offer per pujari per booking ----------------
CREATE UNIQUE INDEX ux_booking_assignments_one_live
    ON booking_assignments (booking_id, pujari_id)
    WHERE responded_at IS NULL;

-- ---- geo: make dispatch radius queries implementable ------------------------
ALTER TABLE addresses ADD COLUMN geom GEOGRAPHY(POINT, 4326);
ALTER TABLE pujari_live_location ADD COLUMN geom GEOGRAPHY(POINT, 4326);
CREATE INDEX ix_pujari_live_location_geom ON pujari_live_location USING gist(geom);

CREATE TABLE pujari_service_areas (
    pujari_id        UUID NOT NULL REFERENCES pujaris(id) ON DELETE CASCADE,
    service_area_id  SMALLINT NOT NULL REFERENCES service_areas(id),
    PRIMARY KEY (pujari_id, service_area_id)
);

-- ---- chat: close the spec gap -----------------------------------------------
ALTER TABLE chat_messages ADD COLUMN message_type VARCHAR(10) NOT NULL DEFAULT 'text'
    CHECK (message_type IN ('text','image','system'));
ALTER TABLE chat_messages ADD COLUMN media_url VARCHAR(500);
ALTER TABLE chat_messages ADD COLUMN read_at TIMESTAMPTZ;

-- ---- money headroom ----------------------------------------------------------
ALTER TABLE payouts ALTER COLUMN amount TYPE DECIMAL(12,2);

-- ---- trigger 6: cancellation state gate (same philosophy as accept trigger) --
CREATE OR REPLACE FUNCTION trg_guard_booking_cancel() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.cancelled_at IS NOT NULL AND OLD.cancelled_at IS NULL THEN
        IF OLD.status_id IN (SELECT id FROM status_types WHERE domain = 'booking'
                             AND code IN ('in_progress','completed')) THEN
            RAISE EXCEPTION 'Booking % cannot be cancelled from its current state.', NEW.id;
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER bu_bookings_cancel_guard
    BEFORE UPDATE ON bookings
    FOR EACH ROW EXECUTE FUNCTION trg_guard_booking_cancel();

-- ---- seed additions (idempotent, same contract as seed.sql) ------------------
INSERT INTO status_types (domain, code, label) VALUES
    ('booking', 'payment_pending',  'Payment Pending'),
    ('booking', 'abandoned',        'Abandoned'),
    ('booking', 'failed_no_pujari', 'No Pujari Found'),
    ('booking', 'disputed',         'Disputed')
ON CONFLICT DO NOTHING;
```

Backfill note: `addresses.geom` and `pujari_live_location.geom` are populated
from existing lat/lon at migration time
(`UPDATE ... SET geom = ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)::geography`)
and written by the API on every subsequent insert/update.

## Migration 003 — DDL (apply verbatim after 002)

Canonical file: **`db/migration_003.sql`** (same contents as the block below).
Apply with `psql -f db/migration_003.sql` or Alembic `op.execute()` on the
file contents.

Dual payment models. `total_amount` is always the full service value
(puja + addons − promo). The platform collects ONLY `amount_due_online`
via Razorpay; `amount_due_offline` is settled directly between customer
and pujari (cash / pujari's own UPI) — never through Razorpay.

```sql
-- ---- platform config: advance amount (admin-tunable) ----------------------
CREATE TABLE platform_settings (
    key         VARCHAR(50) PRIMARY KEY,
    value_json  JSONB NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
INSERT INTO platform_settings (key, value_json) VALUES
    ('advance_booking_amount', '{"amount": 250.00, "currency": "INR"}')
ON CONFLICT (key) DO NOTHING;
-- ₹250 = launch default only. Admin: PUT /v1/admin/settings/advance-booking-amount

-- ---- bookings: payment model + amount split (snapshotted at checkout) ------
ALTER TABLE bookings ADD COLUMN payment_mode VARCHAR(20);
ALTER TABLE bookings ADD COLUMN amount_due_online  DECIMAL(10,2);
ALTER TABLE bookings ADD COLUMN amount_due_offline DECIMAL(10,2);

-- Backfill any rows created before 003 (fresh deploy after 002: zero rows)
UPDATE bookings
SET payment_mode       = 'full_online',
    amount_due_online  = total_amount,
    amount_due_offline = 0
WHERE payment_mode IS NULL;

ALTER TABLE bookings ALTER COLUMN payment_mode SET NOT NULL;
ALTER TABLE bookings ALTER COLUMN payment_mode SET DEFAULT 'full_online';
ALTER TABLE bookings ALTER COLUMN amount_due_online SET NOT NULL;
ALTER TABLE bookings ALTER COLUMN amount_due_offline SET NOT NULL;
ALTER TABLE bookings ALTER COLUMN amount_due_offline SET DEFAULT 0;

ALTER TABLE bookings ADD CONSTRAINT ck_bookings_payment_mode
    CHECK (payment_mode IN ('full_online','advance_balance'));

ALTER TABLE bookings ADD CONSTRAINT ck_bookings_amount_split
    CHECK (amount_due_online + amount_due_offline = total_amount);

-- full_online: everything through Razorpay. advance_balance: advance online,
-- balance offline (may be 0 if total <= advance — effectively full capture).
ALTER TABLE bookings ADD CONSTRAINT ck_bookings_payment_mode_amounts
    CHECK (
        (payment_mode = 'full_online'
         AND amount_due_offline = 0
         AND amount_due_online = total_amount)
        OR
        (payment_mode = 'advance_balance'
         AND amount_due_online > 0
         AND amount_due_offline >= 0)
    );

-- ---- offline balance acknowledgement (NOT a platform payment) ---------------
-- Pujari confirms they received the offline portion. Used for UX, disputes,
-- and earnings display — money never touches Razorpay or wallet_transactions.
ALTER TABLE bookings ADD COLUMN balance_collected_at TIMESTAMPTZ;
ALTER TABLE bookings ADD COLUMN balance_collected_by UUID REFERENCES users(id);
ALTER TABLE bookings ADD COLUMN balance_collection_method VARCHAR(20)
    CHECK (balance_collection_method IS NULL
           OR balance_collection_method IN ('cash','upi_direct'));

ALTER TABLE bookings ADD CONSTRAINT ck_bookings_balance_collection
    CHECK (
        (balance_collected_at IS NULL
         AND balance_collected_by IS NULL
         AND balance_collection_method IS NULL)
        OR
        (balance_collected_at IS NOT NULL
         AND balance_collected_by IS NOT NULL
         AND balance_collection_method IS NOT NULL)
    );

-- advance_balance bookings with a balance MUST record collection before complete
-- (enforced in API, not DB — offline money has no gateway to verify)
```

## Migration 006 — DDL (apply verbatim after 005)

Canonical file: **`db/migration_006.sql`**. Duration guard — trigger 5 `NULLIF`,
backfill `duration_minutes = 0` rows, `CHECK (duration_minutes > 0)` on `pujas`
and `bookings` (`NOT VALID` → backfill → `VALIDATE`). See
`spec/plans/SPEC_AMENDMENTS.md` §12.

Apply with `psql -f db/migration_006.sql` or Alembic `op.execute()` on the file
contents. **Required before go-live** — zero-duration bookings void exclusion constraints.

Amount computation at `POST /v1/bookings` (app layer, snapshotted into columns):

```
advance_amount = (SELECT value_json->>'amount'
                  FROM platform_settings
                  WHERE key = 'advance_booking_amount')::decimal
                 -- launch seed default 250.00; admin changes via API anytime

full_online:
  amount_due_online  = total_amount
  amount_due_offline = 0

advance_balance:
  amount_due_online  = LEAST(advance_amount, total_amount)
  amount_due_offline = total_amount - amount_due_online
  -- Razorpay order amount = amount_due_online ONLY
```

Changing `advance_booking_amount` affects **new** checkouts only. Existing
bookings keep the amounts snapshotted at insert — never backfill on setting
change.

`payments.amount` always equals `bookings.amount_due_online` at webhook time.
`payment_splits` / GST / platform_fee are computed on that captured amount only.
Refunds (cancel / auto-refund paths) are capped at `amount_due_online` — the
platform cannot refund money it never collected.

## The do-not-break list (each fixed a real bug found in review)

**Performance review:** Pass 1 audits diff every proposed DB/query change against this table (`spec/plans/CURSOR_PERFORMANCE_REVIEW_PROMPT.md` Layer 1; task `P-PERF-REVIEW-PASS1` in `STATUS.md`). A "performance fix" that weakens any row below is a defect.

| Object | Why it exists |
|---|---|
| `ux_slot_holds_active` — partial unique `WHERE released_at IS NULL` | Flat unique would permanently lock a slot after first use. Partial = only ACTIVE holds conflict. NULL `pujari_id` ("any pujari") holds never conflict — intended. |
| `ex_bookings_pujari_no_overlap` — gist exclusion on (pujari_id, time range) `WHERE pujari_id IS NOT NULL AND cancelled_at IS NULL` | Duration-aware double-booking prevention at ACCEPT time. Requires `btree_gist`. |
| `ex_bookings_intended_no_overlap` — gist exclusion on (intended_pujari_id, time range) `WHERE paid_at IS NOT NULL AND cancelled_at IS NULL` | Duration-aware double-PAYMENT prevention at WEBHOOK time, AND cross-mode overlap prevention at ACCEPT time (trigger 3 writes `intended_pujari_id` on every accept, so paid direct reservations and accepted broadcast bookings live under one constraint). Without it, a late payment can double-sell a slot, and a broadcast accept can silently consume a window another customer already paid a chosen pujari for. |
| `bookings.duration_minutes` (trigger-snapshotted) | Freezes the overlap window at booking time; catalog changes can't reshape existing bookings. |
| `bookings.cancelled_at` + `bu_bookings_cancel_guard` | `cancelled_at` means TERMINATED (customer cancel, sweep abandonment, dispatch exhaustion — all set it). It frees the window via both exclusion-constraint predicates, releases `ux_bookings_no_duplicate_submit` so the customer can re-book, and gates the accept trigger. A terminal booking WITHOUT `cancelled_at` permanently locks the customer out of that slot — never introduce a terminal status that skips it. The guard trigger makes cancelling `in_progress`/`completed` bookings impossible even for buggy app code. |
| `bookings.hold_id` / `intended_pujari_id` / `paid_at` / `dispatch_mode` | Links checkout to supply. `intended_pujari_id` = the COMMITTED pujari (checkout choice in direct mode; written by trigger 3 on every accept in both modes). Original customer choice is auditable via `dispatch_mode` + `booking_assignments`. |
| `trg_set_booking_pujari_on_accept` — `FOR UPDATE` + 4 guards (v2.1) | Serializes concurrent accepts; rejects already-resolved assignments (Guard 0), expired offers (fresh accepts only — idempotent re-fires are not time-checked), cancelled bookings, second pujaris. On first accept, atomically writes `pujari_id` AND `intended_pujari_id` (arming the paid-slot exclusion for broadcast bookings), flips the booking to 'confirmed', and inserts the history row — no layer above can forget the transition. Idempotent re-fire writes nothing twice. Raises loudly if seed data missing. |
| `booking_assignments.responded_at` = **resolved_at** | Set on accept, reject, AND sweep expiry. Both partial indexes (`ix_booking_assignments_sweep`, `ux_booking_assignments_one_live`) key on `responded_at IS NULL` = "live offer". An expiry flip that skips it grows the sweep index unboundedly and blocks future re-offers. |
| `ck_payment_splits_net_nonneg` + trigger-1 raise | A fee/GST misconfiguration can never persist a negative pujari payout for the payout worker to act on. |
| `ix_bookings_status_created` | Supports the abandoned-payment sweep scan (`payment_pending` older than 15 min). |
| `payments.idempotency_key UNIQUE` | Webhook retry cannot double-charge. |
| `ux_payments_one_success_per_booking` | Duplicate Razorpay orders cannot produce two successful captures for one booking. |
| `refunds` + `ux_refunds_one_active_per_payment` | Refunds are retried by a worker with backoff; a payment can never have two live refunds; `failed_permanent` alarms instead of vanishing. `refunds.id` is the idempotency key SENT to Razorpay; `gateway_refund_id` stores the RETURNED id. Stuck 'processing' rows (crashed worker) requeue via `next_attempt_at` — without this they'd block that payment's refunds forever. |
| `trg_refunds_cap_total` (migration 005) | `SUM(succeeded refunds) + new.amount <= payments.amount` — prevents sequential over-refund after `late_payment` + `admin_override`. |
| `trg_addresses_geom_sync` (migration 005) | Keeps `addresses.geom` in sync with lat/lng on every write. Checkout and dispatch `ST_DWithin` depend on `geom`. |
| `ux_booking_assignments_one_live` | Rebroadcast + duplicate task delivery cannot create two live offers for the same pujari on the same booking (duplicate-FCM bug). |
| `booking_dispatch_state` | Round, radius, max-rounds live in one row — the values DISPATCH_FLOW.md's rebroadcast logic compare-and-sets against. |
| `payment_splits.net_pujari_amount` (trigger) | Money math cannot be written inconsistently by app code. Computed on `payments.amount` (= `amount_due_online` only — never the offline balance). |
| `ck_bookings_amount_split` + `ck_bookings_payment_mode_amounts` | The two payment models are mutually exclusive and sum to `total_amount`. A booking cannot silently morph between models after insert. |
| `bookings.amount_due_online` / `amount_due_offline` | Snapshotted at checkout. Refund math, Razorpay orders, and `payment_splits` all key off `amount_due_online`. Offline balance is outside platform money rails. |
| `bookings.razorpay_order_id` + `ux_bookings_razorpay_order_id` | Written at checkout after Razorpay `create_order`. Partial unique prevents one order id mapping to two bookings. Returned on **409** idempotent duplicate so the client can resume Razorpay without minting a new order. |
| `balance_collected_*` columns | Acknowledgement only — NOT a second payment row. Disputes about offline collection route to admin; Razorpay refunds never touch `amount_due_offline`. |
| `platform_settings.advance_booking_amount` | Admin-dynamic advance for `advance_balance` model. Read live at `checkout/quote` and `POST /v1/bookings`; snapshotted onto the booking row — changing the setting never rewrites existing bookings. |
| `promo_usage_counters` + trigger | Atomic per-user promo limit; no check-then-insert race. |
| `pujaris.rating_avg/rating_count` (trigger from reviews) | Cannot drift stale; recomputed on every review write. |
| `auth_sessions.app_context` CHECK, `notifications.app_context` CHECK | Two-app token scoping and notification routing for dual-role users. |
| `auth_sessions.refresh_token_hash UNIQUE` | Token replay/collision protection. |
| `wallet_transactions.reference_type` CHECK, `notifications.related_type` CHECK | Typed polymorphic references. |
| SMALLSERIAL PKs on all lookup tables | Must match SMALLINT FK columns; SERIAL/SMALLINT mismatch fails CREATE TABLE. |

## Column conventions

- PKs: `uuid DEFAULT gen_random_uuid()` (pgcrypto), except lookup tables
  (SMALLSERIAL). All FKs to lookups are SMALLINT.
- Money: `DECIMAL(10,2)` per-transaction, `DECIMAL(12,2)` for aggregates
  (payouts), never float. Timestamps: `TIMESTAMPTZ`.
- Time arithmetic on `scheduled_date + scheduled_time` (refund cutoffs, start
  windows) MUST be computed in `Asia/Kolkata` explicitly — never rely on
  server-default timezone. See ARCHITECTURE.md open items.
- Status values: always resolved via `status_types (domain, code)` — never
  hardcode integer ids in app code or SQL.
- `bookings.cancelled_at` = terminated (any terminal path: customer cancel,
  abandonment, exhaustion). `booking_assignments.responded_at` = resolved
  (accept, reject, or expiry). Both are load-bearing for partial-index and
  exclusion-constraint predicates — see the do-not-break list.
- `payments.status` is immutable once 'success'. Refund state lives
  EXCLUSIVELY in the `refunds` table. Refund amount is ALWAYS capped at
  `bookings.amount_due_online` (for `advance_balance`, policy % applies to
  the advance only — offline balance refunds are between customer and pujari).
  The `payments.status='refunded'` enum value is reserved and unused — do not
  write it.
- `bookings.payment_mode`: `full_online` (100% via Razorpay) or
  `advance_balance` (advance from `platform_settings.advance_booking_amount`
  online + rest offline). Advance amount is **admin-dynamic**; ₹250 is seed
  default only. Chosen at checkout, immutable after insert.
- Geo: `GEOGRAPHY(POINT, 4326)` for distance queries (**Phase 2** pujari dispatch).
  **`addresses.geom` MUST be populated** on every write (migration 005). Checkout
  rejects `geom IS NULL` with 422. **`addresses.service_area_id`** (migration 012)
  is required for launch — display label only; not a dispatch filter at launch.
- **`intended_pujari_id` / `ex_bookings_intended_no_overlap`:** retained even when
  direct booking is disabled at API (§21). Trigger 3 writes `intended_pujari_id` on
  every accept. **Do not drop** these when removing direct-booking UI.
- **Commission base (intentional):** `payment_splits`, platform fee, and GST are
  computed on `payments.amount` (= `amount_due_online` only). The offline
  balance in `advance_balance` mode is never platform revenue and never enters
  `wallet_transactions`. Product policy: default customers to `full_online`
  (see `spec/plans/MASTER.md`).
- `ON DELETE CASCADE` only where the child is meaningless without the parent
  (user_roles, pujari_documents, chat_messages, booking_addons...). Financial
  and audit tables (payments, refunds, reviews, booking_status_history)
  deliberately default to NO ACTION — deleting a parent with money history
  should fail. The `puja_app` DB role has no DELETE grant at all.
